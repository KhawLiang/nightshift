nightshift 背后的处理逻辑

这台 Mac 上每个 Claude Code session 是怎么被发现、判断状态、然后画成一间办公室的。

一句话

Claude Code 自己会把每个 session 的状态写成 JSON 落盘，nightshift 只是读这份现成的注册表，补一次 tmux 面板快照来判断“有没有打了字没发”，然后把结果扔给浏览器画成像素画。没有 agent、没有数据库、没有轮询 API。

数据从哪来

三个来源，全部是本机文件或本机命令：

来源提供什么
~/.claude/sessions/<pid>.jsonpid、sessionId、cwd、tmux 面板引用、status、时间戳。Claude Code 自己写的，不是我们生成的
tmux capture-pane提示符后面已经打了但没按回车的文字
~/.claude/projects/*/<sid>.jsonl最后一条消息，用作悬停提示里的摘要

最不好猜的就是第一条。整个项目能这么小，是因为状态不需要推断，Claude Code 已经写好了。

状态是怎么算出来的

五个状态里只有四个是读来的，draft 是算出来的。判断“打了字没发”要花一次 capture-pane 子进程，所以只对已经停下来的 session 做——正在跑的 session 不可能在等你按回车。

排序的顺序就是产品观点：waiting（卡在权限确认，去点一下）→ draft（字打了没发，去按回车）→ idle（做完了，给活）→ busy（别打扰）。终端版和像素版共用这一份排序。

状态配色

五个色相刻意拉开，在桌前灯带、椅背、显示器指示灯和地面光斑上重复四次，这样扫一眼房间就知道状态，不用读字。

  • busy 打字、屏幕滚代码
  • idle 靠在椅背上，屏幕自己打俄罗斯方块
  • waiting 转过身举手，显示器上一个 !
  • draft 屏幕上一个光标
  • unknown 整个工位 55% 透明

两个时钟

数据和画面是解耦的。拉数据 2 秒一次，画面 60 帧一秒，中间只隔着两个数组。所以窗口一直在动，但服务端每 2 秒才被打扰一次。

房间是怎么排的

一个 tmux session 一间房，同名 session 里的多个 agent 坐同一间。难点不是分组，是画布该多宽——画布宽高比不匹配窗口时，缩放后会留下大片空白。

做法是把 packRooms(list, CW) 写成纯函数：给一个候选宽度，返回排好的房间和总高度。然后 buildRooms() 从最宽那间房起步，每次 +40 试一遍，取宽高比最接近窗口的那个。

点击回程与安全边界

点一张名牌会真的切你的 tmux。这是整个程序唯一会改变机器状态的动作，所以 /api/focus 上了三道闸：

  1. 形状必须是 ^%\d+$，也就是一个 tmux 面板 id，别的一律拒绝。
  2. 这个 id 必须出现在当次实时 collect() 的结果里，不能是历史里见过的。
  3. 只执行 select-window 和 select-pane，永远不调 send-keys，也不拼 shell 字符串。

服务端只绑 127.0.0.1。第三条是重点：能切窗口但不能替你敲键盘，误点最坏的结果是跳错窗口。

为什么是这个 stack

零依赖是刻意的。这东西要在几十个 tmux session 之间随时开着，任何需要 npm install 或者盯着构建进程的方案都会让人懒得开。

层选了什么代价
服务端标准库 http.server没有热重载、没有中间件，但 100 行就够，且不会有依赖过期
前端单个 HTML + canvas 2D手写像素渲染器比用库长，但改完刷新就是全部开发循环
状态不存，每次重读丢历史曲线，换来没有任何需要迁移或清理的东西

HTML 是每次请求重新读盘的，所以改 office.html 然后刷新浏览器就能看到，不用重启服务。
